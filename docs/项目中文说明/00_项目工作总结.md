# Factory MARL 项目工作总结

## 1. 项目当前总体状态

这个项目当前已经形成了一条可以联调的完整主链：

```text
Simulation -> Core -> Perception / NavDP / MARL / Locomotion -> Dashboard
```

其中真正控制闭环的核心链路可以理解为：

```text
Simulation -> Core -> NavDP -> Locomotion -> Simulation
```

`MARL` 当前作为子目标规划模块接入，`Core` 会融合 `MARL`、`NavDP`、`Locomotion` 的输出，并通过 dashboard 对系统状态进行可视化。

---

## 2. 这轮开发与联调中完成的主要事情

### 2.1 Simulation 侧

#### `legacy` 运行线

- 确认了 `legacy` 是当前最稳定、最适合整链联调的 simulation 运行线。
- 调整了 actor 初始位置和 intruder 路线，使其与联调目标一致。
- 将 `intruder` 改成：
  - 默认静止；
  - 加 `--move-intruder` 时沿固定路线移动。
- 修复了 `intruder` 静止时“在空中乱飞”的问题：
  - 当不移动时锁定 root pose 和 root velocity；
  - 保证静态场景测试稳定。
- 修改了机器人在**没有 locomotion 指令时的行为**：
  - 不再每一拍自动回到默认站姿；
  - 现在保持当前关节 target，不强行弹回默认姿态。
- 增加了双视频录制能力：
  - 原有 monitor-wall 合成视频保留；
  - 新增一个正上方俯视相机，并同步录制独立 top-down 视频。


---

### 2.2 Core 侧

- 核对并稳定了 `core` 对 Simulation 状态、传感器、Locomotion observation 的读取与镜像。
- 调整了 `Core -> Locomotion` 的 `body_velocity_command` 生成逻辑：
  - 增加了合理的 `wz`；
  - 一度把 `vy` 从固定 0 改为可用；
  - 提高过前向速度下限，使狗更容易维持在较高巡航速度。
- `NavDP` 规划频率已提升到 `10 Hz`。
- 增强了 dashboard：
  - 增加 `MARL` 页面角色显示；
  - 显示 `decision_mode`、`fallback_active`、`close_frames`；
  - 显示 locomotion 侧 fallback 状态。

#### Core fallback 逻辑

当前 `Core` 已经承担一套近距离接管逻辑：

- 当狗与 intruder 距离进入 `2.0m` 范围时：
  - `Core` 进入近距离接管；
  - 机器人会朝 intruder 方向前进并转向。
- 当距离进一步进入 `0.5m` 范围时：
  - 停止前进；
  - 只保留朝向 intruder 的转向。
- 当 `NavDP` 给出的 path 首尾点间距小于 `0.2m` 时：
  - 认为路径对推进无意义；
  - 直接进入“只转头不前进”的 fallback。
- fallback 转向速度被改成了更强的版本：
  - 误差存在时直接给到 `wz = ±1.0`。

这意味着当前的近距离收口主要由 `Core` 决定，而不完全依赖 `MARL` 或 `NavDP` 的内部判断。

### 2.3 MARL 侧

#### 从旧版服务到 `v9`

- 梳理了原始 `v9` release 的 observation / action 契约。
- 确认原版 `v9` 真实依赖：
  - `22D` observation；
  - role flag；
  - map-based 8 维 lidar；
  - checkpoint 自带 normalization。
- 把主链中的 `marl_service` 改造成了更接近 `v9` 原版输入输出的 service runtime。

#### 从 `v9` 切到 `v13`

- 检查并接入了 `v13` release。
- 确认 `v13` 是 stricter dynamics 版本：
  - agent 速度更低；
  - intruder 速度更低；
  - yaw rate 更严格；
  - capture 条件更苛刻。
- 将主链默认资源切换到 `v13`。

#### `v13_1` 检查与 fallback 逻辑

- 对比了 `v13` 与 `v13_1`：
  - checkpoint/config/主策略运行代码一致；
  - 差异主要集中在 demo / fallback 逻辑上。
- 研究了 `v13_1` 的 closing fallback 和 subgoal commit 逻辑。
- 一度把 `marl_service` 内部 fallback 完整接入。
- 后来又按联调需求关闭过内部 fallback。
- 最终当前状态是：
  - `MARL` 内部 fallback 已重新打开；
  - 但主控制收口仍以 `Core` 的 2m / 0.5m / NavDP-path-span 规则为主。

#### MARL 可观测性增强

- `marl_service` 现在会输出角色信息。
- 为 `marl` 增加了推理 trace 记录：
  - 输入；
  - 角色；
  - observation；
  - normalization；
  - action；
  - 输出 subgoal；
  - spawn snapshot。
- trace 便于后续离线分析模型行为和定位坐标问题。

### 2.4 NavDP 侧

- 重新梳理了 `NavDP` 当前真实输出格式。
- 确认 `NavDP` 主要对外返回：
  - `planner`
  - `waypoints`
- 目前 `Core` 规划频率已提到 `10 Hz`。
- 在 `navdp_service.py` 中增加了终端日志输出：
  - 每次规划会打印本次 waypoint 全列表；
  - 同时打印 count / first / last / planner / start / goal。

这让我们在联调时可以直接通过终端判断：

- NavDP 有没有给 path；
- path 是否只有一个点；
- path 是否首尾差值很小；
- 当前究竟是直线 fallback 还是 real planner。

## 3. 当前最重要的系统行为结论

### 3.1 Simulation 侧推荐

当前最推荐的整链测试入口仍然是：

- `legacy`

而不是 `rebuild`。

### 3.2 MARL 在系统中的角色

当前 `MARL` 的定位是：

- 输出多智能体协同子目标；
- 提供角色分配和策略侧观测；
- 近距离收口不再完全依赖 `MARL` 自身，而由 `Core` 接管。

### 3.3 Core 当前是收口主导层

当前最关键的近距离行为不是在 `marl_service`，而是在 `Core`：

- `2m` 内前冲并转向；
- `0.5m` 内只转头；
- `NavDP` path 近乎无推进时也只转头。

这让系统在复杂联调情况下更可控。

---

## 4. 当前项目的风险点与后续建议

### 4.1 双层 fallback 可能会重叠

现在 `MARL` 和 `Core` 都具备 fallback 能力。

虽然当前控制上是 `Core` 更主导，但后续如果继续演化，建议明确：

- `MARL` fallback 只用于观测与分析；
  或者
- `Core` fallback 只保留极简兜底；
  或者
- 两者通过显式状态机协同。

否则后期会变成“两个层都觉得自己在救场”。

### 4.2 `rebuild` 线还不算收口

虽然做过大量修正，但当前推荐主线仍是 `legacy`。  
如果后续要真正切到 `rebuild`，建议单独开一期，把它做成与 `legacy` 对等的正式 runtime。

### 4.3 Dashboard 继续强化状态判别会很有价值

现在 dashboard 已经很有帮助，后续还可以继续强化：

- NavDP 当前是否给出有效 path；
- path 首尾跨度；
- 是否被 Core 判成 heading-only fallback；
- MARL fallback 与 Core fallback 的并排状态对照。
